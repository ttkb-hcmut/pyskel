\begin{abstract}
  We present PySkel, a formalization of Python semantics in Skel.
  We describe a subset of the Python programming language including assignments,
  function calls, object oriented features, and exceptions.
  This formalization is used to generate an OCaml interpreter and a debugger.
\end{abstract}

\section{Introduction}\label{sec:introduction}

The Python programming language is widely used, from teaching to research and industry. It is quite complex, however, for
instance with its non-intuitive scoping rules. The closest artifacts to an
official Python specification are
the
\href{https://docs.python.org/3/reference/}{\emph{Python Language Reference}}, the
\href{https://docs.python.org/3/library/}{\emph{Python Standard Library}}, and CPython,
the reference implementation written in C. Unfortunately, none of them are given
as a formal semantics and only the latter is executable. For documentation and
teaching purposes, and to provide the foundations for program analysis, it is most
useful to have a formal and executable semantics of a language. We thus propose PySkel, a formal
semantics of Python, written as a Skeletal Semantics~\cite{noizet:hal-03784478}
description, from which an OCaml interpreter can be extracted. Our work is based
on Monat's denotational semantics of Python~\cite{Monat2021}.

The Skeletal Semantics description of a language can be thought as an
interpreter written in a tiny functional languages, called Skel. There are a few features
that distinguish such a description from a usual interpreter. First, Skel allows
for partial and non-deterministic programs with the \skinl{branch} construct.
Next, it is not necessary to specify everything: some types or functions may be
left unspecified, either because they are not crucial to the description of the
language, because they are implementation dependent, or because they are
specified later in an incremental definition. Finally, Skel is a
\emph{syntax} to describe semantics. It is kept as simple as possible to be used
with many tools, such as an OCaml interpreter generator, a debugger, or a Coq
formalization generator.

The paper is organized as follows. We introduce Skeletal Semantics in
Section~\ref{sec:skel}. We focus on two challenging features of Python and their
description in Skel in Section~\ref{sec:scopes} for scopes and
Section~\ref{sec:objects} for object-oriented aspects. We show how to derive an
interpreter in Section~\ref{sec:interp}. We discuss related work in
Section~\ref{sec:related} and conclude in Section~\ref{sec:conclusion}. Our
formal semantics and interpreter are available online.\footnote{\url{https://gitlab.inria.fr/skeletons/pyskel}}

\section{Monadic Skeletal Semantics}\label{sec:skel}
We first describe Skel, the language of Skeletal Semantics, and how it leverages
monadic features to model complex effectful computations in its simple
functional language while keeping readability. We shortly describe the features
we need for PySkel, a longer introduction to Skel and monads is available in~\cite{KhayamSchmitt2023}.

\subsection{Skeletal Semantics}
Consider the Python statement \texttt{x = \(e\)}.
To provide the semantics of this statement, we write a Skel program containing
an evaluation function \skinl{eval_stmt}, which takes a statement as argument.
A first version of this program is represented in Figure~\vref{fig:simpleskel}.

In this example, we start by declaring types.
Some of them are unspecified (they do not have a definition): \skinl{addr},
\skinl{heap}, \skinl{env}, and \skinl{expr}. The first three are
considered implementation-dependent, the \skinl{expr} type for expressions is
specified later.
The \skinl{stmt} type is specified as a data type with a single
constructor. It depends on unspecified types.
Then, we declare two unspecified functions \skinl{eval_expr} and
\skinl{write_env} by giving their types. These functions cannot be specified as
they manipulate data of unspecified types.
Finally, we provide one specified function, \skinl{eval_stmt}, which
inspects one statement using pattern matching and modify some state.
Note that exception handling is not represented here.

\begin{figure}
\centering
\begin{minipage}{0.8\textwidth}
\begin{minted}[custom lexer=true]{sk.py}
type addr, heap, env, id
type expr
type stmt = | SAssign (id, expr)

val eval_expr : (heap, env, expr) -> (heap, env, addr)
val write_env : (env, id, addr) -> env

val eval_stmt ((h:heap), (e:env), (s:stmt)) : (heap, env) =
  match s with
  | SAssign (id, expr) ->
      let (h', e', addr) = eval_expr (h, e, expr) in
      let e'' = write_env (e', id, addr) in
      (h', e'')
  end
\end{minted}
\end{minipage}
\caption{\label{fig:simpleskel}A simple skeletal semantics}
\end{figure}

More precisely, the \skinl{eval_stmt} function takes as arguments a heap, an
environment, and a statement. It pattern-matches the statement, and in the
(only) case it is an assignment of \skinl{id} to \skinl{expr}, it executes the
relevant code. First, it evaluates \skinl{expr}, returning a new heap
\skinl{h'}, a new environment \skinl{e'}, and an address. Indeed, as in Monat's
work~\cite{Monat2021}, the evaluation of an expression returns a heap address.
We then extend the environment with a new binding and return it, alongside
\skinl{h'}. All these steps are sequenced using the \skinl{let p = e1 in e2}
operator, which evaluates \skinl{e1}, matches its result against \skinl{p}, then
evaluates \skinl{e2}.

This simplified code (which does not include control-flow issues such as
returning from a function call or raising an exception) is quite cumbersome, as
we explicitly manipulate the heap and environment at every step. Adding
exceptions requires that we check at every evaluation step that the returned
address is not an exception. To deal with these issues, we show in the next section how to transform
this code in a monadic version that seamlessly propagates such effects.

\subsection{Monadic Style}
The use of monads to add effects to a functional programming language is
well-known~\cite{Wadler1990}. Skel having first-order functions and polymorphic
types, it can be easily equipped with monads. We use some syntactic sugar to
make the resulting code easier to read.

\begin{figure}
\centering
\begin{minipage}{0.6\textwidth}
\begin{minted}[custom lexer=true]{sk.py}
type flag =
  | Ret addr
  | Brk
  | Cont
  | Exn addr
type exn<a> =
  | Cur a
  | Flag flag

type s = ( heap: python_heap
         , global_scope: global_scope
         , scope_heap: scope_heap (* functions (shared) *)
         , scope_stack: list<map<addr>> (* classes (not shared) *)
         )
type r = ( local_env: env
         , builtins: builtins
         )

type m<a> = (r, s) -> (exn<a>, s)

val return<a> (v : a) : m<a> =
  λ(_, s):(r, s) -> (Cur<a> v, s)

val bind<a, b> ((w: m<a>), (f: a -> m<b>)) : m<b> =
  λ(r, s):(r, s) ->
    let (vo, s') = w (r, s) in
    match vo with
    | Cur a -> let fa = f a in fa (r, s')
    | Flag f -> (Flag<b> f, s')
    end

binder @ = bind
\end{minted}
\end{minipage}
\caption{The \texttt{m} Monad}\label{fig:skelmonad}
\end{figure}

The monad we use in our semantics is given Figure~\vref{fig:skelmonad}. It
combines three monads: a \emph{reader monad} to give read-only access to a local
environment and to the built-in values (type \skinl{r}), a \emph{state monad}
for the read-write access to the heap and the scopes (type \skinl{s}), and an \emph{exception monad}
indicating whether the result is a normal value or not (type \skinl{exn<a>},
detailed below).

More precisely, the monadic type we consider is \skinl{m<a>}, where \skinl{<a>} is
a polymorphic annotation. It is defined as \skinl{(r, s) -> (env<a>, s)}: a
computation takes a current environment and state as input, and it returns a
possibly exceptional result and a new state. The type \skinl{exc<a>} is either
\skinl{Cur a}, an actual result of type \skinl{a}, or \skinl{Flag flag},
indication a control-flow breaking result. This flag can signal the return of a
function \skinl{Ret addr}, where \skinl{addr} is the returned value, the
breaking out or continuing of a loop, and an exception \skinl{Exn addr} where
\skinl{addr} is the exception object.

A monad is associated with two functions. The function \skinl{return<a>} takes a
pure value of type \skinl{a} and puts it in the monad as a computation of type
\skinl{m<a>}. Its code in Figure~\vref{fig:skelmonad} is
\skinl{λ(_, s):(r, s) -> (Cur<a> v, s)}: it is an anonymous function that takes
a pair \skinl{(_,s)}, where the environment is ignored. It then returns a normal
result \skinl{Cur<a> v} alongside the unchanged state \skinl{s}. This code shows
that constructors of polymorphic types must be annotated with the instantiation
type. The function \skinl{bind<a,b>} takes a computation \skinl{w} of type
\skinl{m<a>}, a continuation \skinl{f} of type \skinl{a -> m<b>} (given a pure
value of type \skinl{a}, return a computation of type \skinl{m<b>}), and it
chains them together to return a computation of type \skinl{m<b>}. To this end,
it first takes the current environment and state (\skinl{λ(r,s):(r,s) -> ...}). It
then run the computation \skinl{w} by giving it the environment and the state,
which return a potentially exceptional value \skinl{vo} and a new state
\skinl{s'}. If the value is a pure value \skinl{Cur a}, then the continuation is
called with it as well as with the initial environment and the modified
state.\footnote{Skel is so simple that it does not have n-ary application, hence
  the application of \skinl{f} to \skinl{a} and \skinl{(r,s')} must be done in
  two steps with a let-binding.} If the result is a flag, then the continuation
is not called and the flag is directly returned, changing its type to the
expected output type.

To streamline notations, a symbol can be associated to a binder (\skinl{binder @
= bind}), so that code of the form \skinl{bind e1 (λv -> e2)} can be simply
written \skinl{let v =@ e1 in e2}.
This is similar to OCaml's \texttt{(let*)} and Haskell's leftarrows in \texttt{do}-notation.
The resulting Skel code is given in Figure~\vref{fig:monadiceval}, where the
result of the \skinl{eval_stmt} function lives in the \skinl{m<()>} monadic
type, i.e., computations that return unit.

\begin{figure}
\centering
\begin{minipage}{0.5\textwidth}
\begin{minted}[custom lexer=true]{sk.py}
val eval_expr : expr -> m<addr>
val write_env : (id, addr) -> m<()>

val eval_stmt (s: stmt) : m<()> =
  match s with
  | SAssign (x, v) ->
    let addr =@ eval_expr v in
    write_env (x, addr)
\end{minted}
\end{minipage}
\caption{\label{fig:monadiceval}Monadic Skeletal Semantics}
\end{figure}

\subsection{Specificity of Python Semantics}
The semantics of Python is quite classical, but some points deserve special attention.
In particular, the management of scopes and captures differs from most
functional languages (Section~\ref{sec:scopes}).
We also focus on the object oriented features (Section~\ref{sec:objects}) and
the management of the initial state of the interpreter (Section~\ref{sec:interp}).

\section{Scopes}\label{sec:scopes}
We describe in this section the main concepts of scopes management in Python and their implementation in Skel.
We focus on functions in this section, the scopes for class have some subtleties
that are detailed in Section~\ref{sec:objects}.

\subsection{Scopes in Python}
\begin{figure}
  \centering
  \begin{minipage}[t]{0.2\textwidth}

Scopes in Python are lexical, and correspond to the embedding of function
declarations. The outermost scope is the \emph{global scope}. When accessing a
variable, the local scope is first explored, then the surrounding scope, up
until the global scope. This is illustrated by the first program of
Figure~\ref{fig:scopeillustration} which prints in order \texttt{2}, then
\texttt{1}, then \texttt{0}.

There is no notion of variable declaration in Python to state that a variable
should be added to a scope. The first
syntactic occurrence of an assignment to a variable corresponds to a declaration
of this variable in the current scope. To illustrate this,
consider the second program of Figure~\vref{fig:scopeillustration}. The inner
function has a local \texttt{x} which is set to \texttt{1}, so the scope of
\texttt{foo} has this variable. Hence, the program first
prints \texttt{foo:1} for the local \texttt{x} when \texttt{foo} is called, then \texttt{global:0} for the
global (different) \texttt{x}.

To tell Python that an assignment is not a variable declaration, one should
state the scope of the variable to modify before any assignment, so that this
assignment does not declare the variable. One may state that a variable is
global, as shown in the third program. This programs prints \texttt{foo:1} and
\texttt{global:1}, illustrating that the assignment in \texttt{foo} did change
the global \texttt{x}. Note that the global annotation for a variable also
impacts how it is read. The following code for instance outputs \texttt{3}.
Indeed, as \texttt{x} is not defined in \texttt{baz}, it is looked up in
\texttt{bar}, where it is said to be global.
\begin{minted}{python}
x = 3
def foo():
    x = 1
    def bar():
        global x
        def baz():
            print(x)
        baz()
    bar()
foo()
\end{minted}

Alternatively, a variable assignment may refer to an enclosing scope that is not the global
scope. This is illustrated in the fourth program, where \texttt{x} is local to
the function \texttt{foo}. In the enclosed function \texttt{bar}, \texttt{x} is
declared as \texttt{nonlocal}, which means it must be declared in an enclosing
function. It does not have to be the immediately enclosing function, and it
cannot be the global scope.

Note that the \texttt{global} and \texttt{local} keywords only matter for
writing variables, and that they are syntactic constructs: the variable written
by an assignment is statically known when parsing the program. However, with the
exception of the global scope, scopes are created at run-time (for instance when
calling a function), and they may persist after the function's completion.
Consider the following code.
\begin{minted}{python}
def counter(init):
  x = init
  def reset():
    nonlocal x
    x = 0
    print(x)
  def incr():
    nonlocal x
    x = x + 1
    print(x)
  return(reset,incr)

r,i = counter(5)
i(); r(); i()
\end{minted}
After calling \texttt{counter}, the two returned functions share its scope as
enclosing scope, where the nonlocal variable \texttt{x} is defined. The
code thus prints \texttt{6}, \texttt{0}, then \texttt{1}.

Note that scopes are computed at parsing time: when a function is called, its local variable are allocated but not initialized yet.
Thus, reading an uninitialized variable in a function definition results in an
\texttt{UnboundLocalError} instead of the \texttt{NameError} that occurs when a
variable does not exists. This is illustrated by the following code.
\begin{minted}{python}
def f():
  x = undef # raises NameError as undef does not exists
  x = y     # raises UnboundLocalError because y is local to f but not yet bound
  y = 0
\end{minted}

\subsection{Scopes in PySkel}
PySkel extends Monat's semantics with the previously described scopes.
We now distinguish two types of scopes, each representing a mapping from identifiers to values, but with some special properties.

First, we define a global scope, containing the top level functions and values.
The global scope is unique and shared, with a simple structure.
In Skel, it is defined as \mintinline[custom
lexer=true]{sk.py}{type global_scope = map<addr>}, i.e., a mapping from strings
to adresses (see below).
It is part of the mutable state described Figure~\vref{fig:skelmonad}.

We next introduce the type of function scopes.
As these scopes may contain uninitialized values, we define a
\texttt{partial_addr} type, isomorphic to Haskell's well-known \texttt{Maybe}
type\footnote{We could also use the \texttt{maybe} type, but we define a new one to clarify the code.}, with a \mintinline[custom lexer = true]{sk.py}{LocalUndef} constructor.
In addition, function scopes can be shared and access upper scopes.
To do this, we define an additional heap for scopes, so scopes are allocated and
referenced with \emph{scope identifiers}.

Scopes are a data structure to organize identifiers, but we need extra information.
For example, to execute a variable assignment, one should know in which scope to look for it (i.e., is the variable local, global, or nonlocal).
To this end, scopes are accompanied by a map from variable names
to \skinl{type var_scope = Local | Nonlocal | Global}.
This map is built as follows: global and nonlocal variables are explicitly given, and the remaining
assignments are local variable declarations.
So we need two things to manipulate variables in a function: the scope and the location map.

A function scope is thus a pair of a map from strings to \skinl{partial_addr}
for the scope contents and an optional \skinl{scope_info} for the enclosing scope.
The final type is presented below.
%\asi{define maybe and map, explain why you don't use maybe for partial\_addr.
%  Also define the polymorphic types heap\_addr and heap, especially since the
%  heap of Fig 1 is not polymorphic.}
\begin{minted}[custom lexer=true]{sk.py}
type heap<_> (* Unspecified heap, heap<a> contains values of type a *)
type heap_addr<_> (* heap_addr<a> are the addresses of heap<a> *)

type map<_> (* Unspecified map, map<a> is a mapping from strings to a *)
type maybe<a> = | Nothing | Just a

type partial_addr = | LocalUndef | Value addr
type var_scope = | Local | NonLocal | Global

type scope_info = (scope_id, map<var_scope>)
type partial_scope = (pmapping: map<partial_addr>, pscope_up: maybe<scope_info>)

type scope_id = heap_addr<partial_scope>
type scope_heap = heap<partial_scope>
\end{minted}

The \skinl{var_scope} map is not part of the \skinl{partial_scope} type.
This is because the map is read-only in a function, and we thus avoid to store it in the mutable state.

Note that the \texttt{heap} type is parameterized while the one presented Figure~\vref{fig:simpleskel} is not.
As a result need to specify the type of values stored in the main Python heap.
It is well described in Monat's semantics (the two sets \textsf{ObjN} and \textsf{ObjS}), and can be translated straight to Skel.
Heap values are composed of two elements, respectively of type \texttt{obj_n} and \texttt{obj_s}.
The \texttt{obj_n} type represents the different kinds of values (\mintinline[custom lexer = true]{sk.py}{Int}, \mintinline[custom lexer = true]{sk.py}{String}, \mintinline[custom lexer = true]{sk.py}{Fun (..)}, etc).
The \texttt{obj_s} part is a dictionary containing the fields of a value.
We thus define the \texttt{heap} type as follows.
\begin{minted}[custom lexer = true]{sk.py}
type obj_n = | Int python_int | String python_string | ...
type obj_s = | Locked | Fields map<addr>

type addr = heap_addr<(obj_n, obj_s)>
type python_heap = heap<(obj_n, obj_s)>
\end{minted}
The \texttt{obj_n} type contains a constructor \skinl{Fun} for functions, this
constructor includes a \texttt{scope} field indicating the scope where the
function has been defined.

\subsection{Function Call and Memory Access}
We summarize in this part the different actions performed to evaluate a function.
The goal of this part is to provide a global understanding of functions and to justify the design of scopes.

\subsubsection{Function Declaration}
Evaluating a function declaration statement consists to allocate a \skinl{Fun} object on the heap.
This is easily done by extracting the local variables of the function.
The \skinl{scope} field is set to the current scope information.
If the function is top level, we set it to \skinl{Nothing}.

\subsubsection{Function Call}
To call a function, we first extract the \skinl{Fun} object from the heap.
This object contains the arguments and the local variables to the functions.
We add these variables to a freh scope, where the arguments are bound to their value and locals to \skinl{LocalUndef}.
We set the \skinl{pscope_up} field of the fresh scope to the scope information stored in the \skinl{Fun} object.

Then, the var map must be computed (as it is not stored in the \skinl{Fun} object, this is a design choice to keep the \skinl{obj_n} type close to the original semantics) by inspecting the body of the function.
Once this is done, we can evaluate the body with the new scope information.
In concrete terms, we locally change the read-only environment to \skinl {InFun (fun_scope, var_map)}.

The environment, first declared Figure~\vref{fig:skelmonad}, keeps track of the evaluation context.
This context can have three forms: \skinl{Globl}, \skinl{InFun} or \skinl{InClass}.
\skinl{Globl} means ``In the global scope'', or ``At top level'', it does not provide any additional information.
The \skinl{InFun} state contains a \skinl{scope_info} and represents the evaluation of a function.
The \skinl{InClass} is described in the next section.
We need to build able to distinguish between contexts because the scoping rules are different in a function, a class or at toplevel.

\subsubsection{Memory Access}

To read or write a variable in a function, we first look at the \skinl{var_scope} associated to the variable to know if it's local, nonlocal or global.
We can then look for the variable in the right scope:
\begin{itemize}
\item The identifier of the local scope is in the read-only state,
\item The upper scope is stored in the local scope,
\item The global scope is stored in the mutable state.
\end{itemize}

We first describe the main aspects of Python concerning object-oriented programming, the features we handled that are not part of the semantics and their implementation.

\subsection{Classes in Python}
A class defines a new \emph{type}, it consists of a set of \emph{fields}, declared in the class body.
Classes can inherit from each other, the set of fields of a class and its super classes forms the \emph{attributes} of the class.

This set of fields is a list of statement, just like a function body.
It may contain global and non local variables, declared with the \mintinline{python}{global} and \mintinline{python}{nonlocal} keywords.
The variables so defined are not part of the fields of the class.

The notion of field is hidden in Python, but it is nevertheless necessary to understand the underlying mechanism of classes.
In the code sample given in Figure~\vref{fig:class}, the class \texttt{Example} has three fields: \texttt{value}, \texttt{function} and \texttt{method}.
As the class inherits from \mintinline{python}{Super}, the set of attributes may not be equal to the set of fields.

\begin{figure}[ht]
  \centering
  \begin{minipage}{0.25\textwidth}
    \begin{minted}{python}
class Example(Super):
  value = 0
  def function():
    return 1

  def method(self, value):
    self.x = value
    \end{minted}
  \end{minipage}
  \caption{\label{fig:class}A Class in Python}
\end{figure}

To create an instance of some class, we call the class like a function: \texttt{Example()}.
This creates a reference to the class called.
Instances shares the attributes of the superclass, they can access them with the dot operator: \texttt{Example().value}.
This operator can have some side effects.
In particular, if an instance accesses a function of its class, a new \emph{method} is allocated and returned instead of the function.
This method contains two addresses: the instance and the function.
Thus, the method call simply passes the instance as first parameter to the function.
The given instance is modified according to the function body defined in the class.
This mechanism is illustrated Figure~\vref{fig:method}.

\begin{figure}[ht!]
  \centering
  \begin{minipage}{0.8\textwidth}
    \begin{minted}{python}
class Example:
    def method(self, value):
        self.x = value

instance = Example()

Example.method # is a function
instance.method # is a method, referencing `instance` and `Example.method`
instance.method(2) # is nearly the same as
Example.method(instance, 2) # "nearly" because no method is allocated here
    \end{minted}
  \end{minipage}
  \caption{\label{fig:method}Functions and Methods}
\end{figure}

As can be seen, instances can have additional fields that are not part of the class (\texttt{x} in the example).
Those fields are stored on the heap, next to the object they belong to (It's the structural part \textsf{ObjS}).



As classes are well described in the original semantics, they are not studied any further in this article.
However, we've changed the semantics of functions, so we need to explain how classes are affected by this change.
In the next part, we show how classes are impacted by the addition of scopes.

\subsection{Classes in PySkel}
In PySkel, classes representation contains a map from identifiers to addresses, for the fields.
It is the only non trivial part to compute when evaluating a class definition.
Classes' bodies are close to functions' ones, with \mintinline{python}{global} and \mintinline{python}{nonlocal} variables, so a first idea would be to allocate a fresh \emph{function} scope and evaluate the body in it.
The entries of the scope would be the fields of the class.
We do something very similar in PySkel, the only difference is the scope type: functions scopes are designed for functions and are not adapted to class evaluation.
To understand the need of a new scope type, we must clarify the differences between classes and functions.

First classes variables cannot be uninitialized, so we don't need partial maps and \texttt{LocalUndef}.
Then, fields exist only in the class, they are not accessible in subfunctions or subclasses, so the scope chain need to bypass classes (see example figure~\vref{fig:classscope}).
Finally, classes scopes cannot be shared and modified by others, so we do not need to store them on the heap.

\begin{figure}[ht]
  \centering
  \begin{minipage}{0.2\linewidth}
    \begin{minted}{python}
def foo():
    x = 0
    class C:
        x = 1
        def bar():
            print(x)
    return C

foo().bar() # 0
    \end{minted}
  \end{minipage}
  \caption{\label{fig:classscope}Scopes interaction between functions and classes.}
\end{figure}


Hence, we need a simple address map, like the global scope, with some upper scope for nonlocal variables.
In case of nested classes, we may need to pause the current class scope to evaluate the subclass.
This is why we have a \texttt{scope_stack} in the mutable state.
At any point of the program, the length of the stack corresponds the number of classes we entered to reach the program point.
Once the body of the class is fully evaluated, we pop the scope from the stack to obtain the expected dictionary.

The final type of the environment below.
The \skinl{Globl} and \skinl{InFun} constructors have been introduced in the previous section.
For classes, the context is composed of the \skinl{var_scope} map and the upper scope information.
The current scope is at the top of the stack, we do not need a scope identifier.
\begin{figure}[h]
  \centering
  \begin{minipage}{0.55\linewidth}
    \begin{minted}[custom lexer = true]{sk.py}
type env =
  | Globl
    (* var_scope and current scope *)
  | InFun scope_info
    (* var_scope and scope_up *)
  | InClass (map<var_scope>, maybe<scope_info>)
    \end{minted}
  \end{minipage}
\end{figure}


\section{Deriving an Interpreter}\label{sec:interp}
Once the semantics is written, we can use the various Skel backends to test and demonstrate the usability of the semantics.
We describe in this part the process of deriving a Python interpreter.

\subsection{Project Structure}
The Skel toolchain contains a program called \texttt{necroml}.
It takes a Skel semantics and translate it to an OCaml interpreter.
The generated code takes the form of a functor requiring an implementation of
the unspecified types and terms.
PySkel uses \texttt{necroml} to derive a simple Python interpreter which is used to test the semantics.
For a better understanding of the PySkel project structure, we provide a summary
diagram in Figure~\vref{fig:pyskel}.

The \texttt{necroml} program generates specified terms and requires an implementation of unspecified ones.
This implementation is written in OCaml and it part of the PySkel project.
With this two parts, a functor instantiation gives the Python interpreter.
We can run this interpreter by providing a program and some initial state (which
correspond to the state part the monad).
This state is computed from a prelude file containing the builtin classes (such as exceptions) and some glue to fit well with the Skel semantics (see Section~\vref{sec:internal function}).
Python programs are parsed with the \texttt{pyre-ast} OCaml library and then translated to the PySkel AST.
The whole code is available at the following url: \href{https://gitlab.inria.fr/skeletons/pyskel}{\url{https://gitlab.inria.fr/skeletons/pyskel}}.

The unspecified part of PySkel is small.
It is composed of primitive types (\texttt{bool}, \texttt{int}), functions that
operate on these types, the heaps, and a polymorphic map from strings.
The implementation is 100 lines long, compared to 1200 lines of Skel.

\subsection{Initial State and Internal Function}\label{sec:internal function}
The evaluation of a Python program requires some initial state.
This state must contain builtin objects, functions and classes.

As the organization of builtin functions are not really part of Python evaluation mechanism, we do not want to specify it in the semantics.
Note that functions are defined in the semantics, but not organized in classes.
For example, the addition of integers is written in the Skel file, but not linked to any \texttt{int} class or \texttt{__add__} method.
Hence, we need a way to organize existing Skel code into classes from outside the semantics.

This is done with a Python \emph{prelude} file, containing declaration of classes and methods.
We provide a way to link Skel code with a decorator \mintinline{python}{@pyskel_internal}.
The writter of the prelude file must specify a token name (\mintinline{python}{"IntAdd"} in the example) to identify the corresponding code.
We can understand this as ``when you try to call this function, call the Skel code associated to the \mintinline[custom lexer = true]{sk.py}{IntAdd} token instead''.
\begin{figure}[ht]
  \centering
  \begin{minipage}{0.3\linewidth}
    \begin{minted}{python}
class int(object):
    @pyskel_internal("IntAdd")
    def __add__(self, other):
        pass
    \end{minted}
  \end{minipage}
\end{figure}

Then, in the semantics, the \texttt{call_internal} function redirects the call to execute the desired code, as shown Figure~\vref{fig:call internal}

\begin{figure}[ht]
  \centering
  \begin{minipage}{0.9\textwidth}
    \begin{minted}[custom lexer=true]{sk.py}
type internal = | IntAdd

val call_internal ((internal : internal), (args : list<addr>)) : m<addr> =
  match internal with
  | IntAdd ->
     match args with
     | Cons (op1, Cons (op2, Nil)) ->
       let (objn1, _) =@ read op1 in
       let (objn2, _) =@ read op2 in
       match (objn1, objn2) with
       | (Int left, Int right) ->
          let result = internal_int_add (left, right) in
          alloc (Int result, Fields map_empty<addr>)
       | _ ->
          let r =@ ask in
          ret r.builtins.notImplemented
       end
     | _ ->
        raise_exn<addr> _TypeError
     end
  end
    \end{minted}
  \end{minipage}
  \caption{\label{fig:call internal}\texttt{call_internal} function in the Skel semantics}
\end{figure}

The connection between the decorator and the internal call is done during the
translation from the Pyre AST to the Skel AST.

\section{Related Work}\label{sec:related}
There have been several proposals to formalize the semantics of Python. Monat gives a denotational
semantics (on paper) in his PhD thesis~\cite{Monat2021}, which is used to build analyzers
as part of the MOPSA platform~\cite{MonatOuadjaoutMine2021}. His semantics is quite faithful as it
is derived from the official Python interpreter written in C. Our work is
heavily based on this semantics, extended to deal with additional features
absent from Monat's thesis, such as nonlocal and global scopes. We also provide
an interpreter, whereas Monat's semantics is not executable. In addition, our
Python semantics is written in Skel, so it can easily be reused for other tools.
We have for instance used the Necro debugger~\cite{necrodebug} to execute our semantics
step by step.

An initial attempt to formalize the semantics of Python was done by Politz et
al. as a small-step operational
semantics~\cite{PolitzMartinezMilanoWarrenPattersonLiChitipothuKrishnamurthi2013}.
This semantics is actually given as a translation, called \emph{desugaring}, of Python in
\(\lambda_{\pi}\), a much smaller core language. The desugaring process and an interpreter for \(\lambda_{\pi}\)
are both written in Racket~\cite{FelleisenFindlerFlattKrishnamurthiBarzilayMcCarthyTobin-Hochstadt2018}. When combined, they provide an
interpreter for Python source code. We have relied on this work to
grasp the subtlest aspects of Python's scopes, in particular for classes defined
inside functions. The distinguishing feature of our work compared to theirs is
that we describe the semantics directly at the source code level. The desugared
semantics can be quite different from the source, especially when it is
CPS-transformed to deal with generators. Understanding the semantics of a Python
program by looking at an execution of its desugared version may be challenging.
Although we have not yet implemented generators, we discuss how we plan to
seamlessly handle them in Section~\ref{sec:conclusion}.

Finally, some recent work aims at giving a semantics of Python's bytecode
through a formalization in F*~\cite{Karkour2022}. Once again, it is challenging
to reason about a source program through the semantics of a translation, here
into bytecode.

\section{Conclusion and Future Work}\label{sec:conclusion}
We presented PySkel, a formalization of Python semantics in Skel, which we used
to derive a Python interpreter in OCaml. The development of this complex
semantics has helped identify areas of improvement for Necro, such as the
inclusion of files. Although our formalization only cover a tiny subset of the
standard library, we believe it is illustrative enough to be easily extended.

Regarding generators, we plan to reuse the work of Khayam et al.~\cite{KhayamSchmitt2023} to
capture their semantics through a delimited continuation monad. More precisely,
they have shown that, since Skel is almost in administrative normal
form~\cite{SabryFelleisen1992}, one may choose an appropriate monad to seamlessly capture
side-effects, including the interruption of a computation because of a
\texttt{yield}.
