\begin{abstract}
  We present Pyskel, a formalization of Python semantics in Skel.
  We describe a subset of the Python programming language including assignments,
  function calls, object oriented features and exceptions.
  This formalization can be used to automatically derive interpreters and debuggers.
\end{abstract}

\section{Introduction}\label{sec:introduction}

The Python programming language is widely used by programmers,
but it lacks an official and clear specification, the
\href{https://docs.python.org/3/reference/}{\emph{Python Language Reference}} and
\href{https://docs.python.org/3/library/}{\emph{Python Standard Library}}
begin the closest things to it.

A formal specification of a programming language is necessary to prove properties on programs.
Moreover,

We propose a Skel implementation of Raphaël Monat's Python pure semantics\cite{Monat2021},
as mentionned in~\cite{noizet:hal-03784478}.

\section{Monadic skeletal semantics}
The semantics desbribed in the paper is written in the Skel language.

A skeletal semantics can be seen as an interpreter, were some functions and types are left unspecified.
This allows to express the semantics independently of the implementation choices.

\subsection{A simple skeletal semantics}
Consider the Python statement \texttt{x = \(e\)}.
To provide the semantics of this statement, we write a Skel function \texttt{eval\_statement}, which accept a statement as argument.
A first version of this function is represented figure~\vref{fig:simpleskel}.

\begin{figure}[ht!]
\centering
\begin{minipage}{0.8\textwidth}
\begin{minted}[custom lexer=true]{sk.py}
type addr, heap, env
type expression
type statement = | SAssign (id, expression)

val eval_expression : (heap, env, expression) -> addr
val write_env : (env, id, addr) -> env

val eval_statement (heap, env, stmt) =
  match stmt with
  | SAssign (id, expr) =
      let (heap, env, addr) = eval_expression (heap, env, expr) in
      let env = write_env (env, id, addr) in
      (heap, env, ())
\end{minted}
\end{minipage}
\caption{\label{fig:simpleskel}A simple skeletal semantics}
\end{figure}


This code deserves further explanation:
This semantics contains a function \texttt{eval\_statment}, this function is our interpreter.
It takes a statement and modify the state accordingly.
Note that exception handling is not represented here.
The actual code would be even more complex, involving sum types and pattern matching at each function call.

The state is, for now, a heap and an environment.
When a python expressions is computed (through \texttt{eval\_expression}), we get an heap address.
The actual Skel representation of the result is stored inside the heap.
The environment is a map from identifiers to values.

This code is unnecessarily cumbersome.
The interpretor state is made explicit at each function call, and modifications are handle but the code writer.
We present in the next part a monadic version of the semantics, more adapted to our needs.

\subsection{Monadic style}
By using a monadic style, we can hide the state to functions which don't need it.
It also make the code closer to an imperative language.

Here is the monad we use in our semantics:
\begin{figure}
\centering
\begin{minipage}{0.6\textwidth}
\begin{minted}[custom lexer=true]{sk.py}
type flag =
  | Ret addr
  | Brk
  | Cont
  | Exn addr
type exn<a> =
  | Cur a
  | Flag flag

type s = ( global_scope: global_scope
         , heap: pythonHeap
         , scope_heap: scope_heap
         )
type r = ( local_env: env
         , builtins: builtins
         )

type m<a> = (r, s) -> (exn<a>, s)

val return<a> (v : a) : m<a> =
  \(_, s):(r, s) -> (Cur<a> v, s)

val bind<a, b> ((w: m<a>), (f: a -> m<b>)) : m<b> =
  \(r, s):(r, s) ->
    let (v, s') = w (r, s) in
    match v with
    | Cur a -> let fa = f a in fa (r, s')
    | Flag f -> (Flag<b> f, s')
    end
\end{minted}
\end{minipage}
\caption{\label{fig:skelmonad}The \texttt{m} monad}
\end{figure}

The two types \texttt{r} and \texttt{s} represent the read-only and read-write state of the interpreter.
The \texttt{exn} is used for control flow operations, such as \texttt{return} statement handling or exceptions.

This results in the following Skel code, with type annotations:
\begin{figure}[ht!]
\centering
\begin{minipage}{0.5\textwidth}
\begin{minted}[custom lexer=true]{sk.py}
val eval_statement (s: stmt) : m<()> =
  match s with
  | SAssign (x, v) ->
    let addr =@ eval_expr v in
    write_env (x, addr)
\end{minted}
\end{minipage}
\end{figure}

\subsection{Specificities of Python Semantics}

\section{Scopes}
We describe in this section the main concepts of scopes management in Pyhton and their implementation in the skeletal semantics.
We will focus on functions, classes' scopes have a few differences which will be explained in the corresponding section.

\subsection{Scopes in Python}
Python does not have a syntax criteria to distinguish between declarations and assignments. Consider the programs Figure \vref{fig:scopeillustration}:
\begin{figure}[ht]
  \centering
  \begin{minipage}{0.3\textwidth}
    \begin{minted}{python}
x = 0
def function():

  x = 1
  print(x)

function(); print(x)
    \end{minted}
  \end{minipage}
  \begin{minipage}{0.3\textwidth}
    \begin{minted}{python}

x = 0
def function():
  global x
  x = 1
  print(x)

function(); print(x)
    \end{minted}
  \end{minipage}
  \begin{minipage}{0.3\textwidth}
    \begin{minted}{python}
def wrapper():
  x = 0
  def function():
    nonlocal x
    x = 1
    print(x)

  function(); print(x)
wrapper()
    \end{minted}
  \end{minipage}
  \caption{\label{fig:scopeillustration}Scopes Behavior}
\end{figure}

The first one will output \texttt{1} and \texttt{0}: by default, assignments are declarations.
The first code sample contains to variables named \texttt{x}: the global one (equal to zero), and one local to \texttt{function} (equal to one).

To use the global version of \texttt{x} in \texttt{function}, the \texttt{global} keyword must be used.
This meaning is ``Some variable \texttt{x} is already defined in the global scope, use this one instead of creating a new one''.
The second program will therefore display \texttt{1} and \texttt{1}.

One trickier case is the third program.
It is very close to the second one but with one little difference: the entire code is place in a function (called \texttt{wrapper} in the example).
To use the \texttt{x} variable defined in the \texttt{wrapper} function inside of \texttt{function}, we cannot use the \texttt{global} keyword, because \texttt{x} is not \texttt{global}.
In this case, the \texttt{nonlocal} keyword is what we need.
It uses the closest definition of \texttt{x} among the upper scopes.
Like the second one, it displays two \texttt{1}.

To summarize, the \emph{global scope} contains all the toplevel declarations, it is a mapping from variable names to heap addresses.
The local variables of a function and its parameters are stored in the scope associated with the function.


Functions may need to access upper scopes, especially in case of reads to non local variables.
We depict this dependency as a tree of scope, as shown in figure \vref{fig:functionscope}.

Note that scopes are computed at parsing time: when a function is called, its local variable are allocated but not initialized yet.
Thus, reading a not yet defined variable in a function definition will result in an \texttt{UnboundLocalError} instead of a classical \texttt{NameError}. This is illustrated figure \vref{fig:unboundlocal}.

\begin{figure}[ht!]
  \centering
  \begin{minipage}{0.5\textwidth}
  \begin{minted}{python}
def f():
  x = undef # will raise NameError
  x = y     # will raise UnboundLocalError
  y = 0     # because y is local to f
  \end{minted}
  \end{minipage}
  \caption{\label{fig:unboundlocal}Example of a program throwing \texttt{UnboundLocalError}}
\end{figure}

\subsection{Scopes in Pyskel}
Pyskel Scopes are by designed the exact representation of scope trees given Figure~\vref{fig:functionscope}.
As it is possible to have multiple references to the same scope, we use a key-value mechanism to make the scopes mutable.


\begin{description}
\item[Total scopes] are mapping from identifiers to heap addresses, they are represented by the following type:
  \begin{minted}{python}
type total_scope = (tscope_up: maybe<scope_id>, tmapping: map<addr>)
  \end{minted}
  The definition is straight forward, a total scope is a mapping and some optional scope.
  the \texttt{tscope\_up} is used to look up nonlocal variables.
\item[Partial scopes] can accept uninitialized values, we use an option type to represent this property:
  \begin{minted}{python}
type maybe<a> =
  | Nothing
  | Just a

type partial_scope = (pscope_up: maybe<scope_id>, pmapping: map<maybe<addr>>)
  \end{minted}
\end{description}

Note that scope identifiers are also useful for the tree structure of the scope. A partial scope can be defined in a total scope and vice versa.
The link betwin scope ids and scopes is done with a map of \texttt{any\_scope}:
\begin{minted}{python}
type any_scope = | TotalScope total_scope
                 | PartialScope partial_scope
\end{minted}


\section{Objects and Classes}
Python values are stored on the \emph{heap}.
Formallly, the heap is a mapping from addresses to Python objects, such as:
\begin{itemize}
\item Constants (integers, strings, booleans, \dots)
\item Functions and methods
\item Classes and intances
\end{itemize}

We describe in this section the Object-Oriented features of Python and the Skel implementation.

\subsection{Classes}
A class defines a new \emph{type}, it consists of a set of \emph{fields}, declared in the class body.
Classes can inherit from each other, the set of fields of a class and its super classes form the \emph{attributes} of the class.


The notion of field is hidden in Python, but it is nevertheless necessary to understand the underlying mechanism of classes.
In the code sample giver figure~\vref{fig:class}, the class \texttt{Example} has three fields: \texttt{value}, \texttt{function} and \texttt{method}.
As the class does not inherit, the set of attributes is equal to the set of fields.

\begin{figure}[ht]
  \centering
  \begin{minipage}{0.25\textwidth}
    \begin{minted}{python}
class Example:
  value = 0
  def function():
    return 1

  def method(self, value):
    self.x = value
    \end{minted}
  \end{minipage}
  \caption{\label{fig:class}A class in Pyhton}
\end{figure}


In Skel, classes are represented by a map from identifiers to addresses and the list of its super classes.
To collect the fields of a class, we first need to evaluate its body.
This evaluation is performed in a new total scope, which provides us directly the class dictionary.

\subsection{Instances}
To create an instance of some class in Python, we call the class like a function like this: \texttt{Example()}.
This will create a reference to the class called.
Instances shares the attributes of the superclass, they can access them with the dot operator: \texttt{Example().value}.
This operator can have some side effects.
In particular, if an instance accesses a function of its class, a new \emph{method} will be allocated and returned instead of the funcion.
This method will contain two addresses: the instances and the function.
Thus, the method call will simply pass the instance as first parameter to the function.
This mechanism is illustrated Figure~\vref{fig:method}.

\begin{figure}[ht!]
  \centering
  \begin{minipage}{0.8\textwidth}
    \begin{minted}{python}
class Example:
    def method(self, value):
        self.x = value

instance = Example()

Example.method # is a function
instance.method # is a method, referencing `instance` and `Example.method`
instance.method(2) # is the same as
Example.method(instance, 2)
    \end{minted}
  \end{minipage}
  \caption{\label{fig:method}Functions and Methods}
\end{figure}


As you can see, instances can have additional fields that are not part of the class (\texttt{x} in the example).
Those fields are store on the heap, next to the object they belong to.
It takes the form of an additional dictionary, stored next its the value on the heap.

In Pyskel, the heap maps integers to pairs \textsf{(ObjN, ObjS)}, respectively for the nominal and structural parts.

\section{Initial State and Internal Functions}
The evaluation of a Python program requires some initial state.
This state must contains builtin object, functions that operates on this object and classes to organize the functions properly.
This elements can be defined in multiple places:
\begin{itemize}
\item In the skel semantics, \texttt{True} and \texttt{False} are two example
\item In the OCaml implementation, if the term is let unspecified in the semantics.
  This is the case for integer addtition, since intergers are not specified.
\item In a prelude Python file, which contains the builtin classes.
\end{itemize}

\section{Conclusion and future works}
We presented a formalization of Python semantics in Skel, and used this semantics to derive a python interpreter.
This work has led to the improvement of the necro ecosystem, necrodebug in particular.

Some points in the python semantics are not covered by pyskel yet, such as generators, a large part of the standard library.
